# 外電通信サイト：テーマ実装ルール

この文書は、外電通信サイトで新しい「お着替えテーマ」を設計・実装する際の**実装上の正本**です。

Figma、Codex、ChatGPT、その他のAIや人間の実装者は、テーマ作業を始める前にこの文書を読んでください。

設計思想の背景は [`DESIGN_ARCHITECTURE.md`](DESIGN_ARCHITECTURE.md) を参照してください。両者が重なる場合、実装手順・保護対象・退避手順についてはこの文書を優先します。

---

## 1. このサイトの基本思想

外電通信サイトは、**内容は長く残し、外観は定期的に着替える**サイトです。

テーマは単なる装飾ではなく、その時点のWebデザインや表現技術を試すための実験場所でもあります。新しいテーマでは、先進的なデザイン、実験的なレイアウト、最新のCSSやブラウザ機能、新しいタイポグラフィやモーション表現などを積極的に検討して構いません。

ただし、実験対象はあくまで**見せ方**です。掲載内容、URL、意味構造、情報公開の継続性は実験対象にしません。

このリポジトリでは次の4層を分けて考えます。

1. **Content — 内容の正本**
2. **Theme — 定期的に交換する衣装**
3. **Plain — いつでも戻れる安全地帯**
4. **Static fallback — Astro自体が使えないときの最後の退避先**

最重要原則は次の一文です。

> **テーマは壊してもよいが、内容と退避経路は壊さない。**

---

## 2. 正本と役割

```text
src/content/pages/gaiden.md          掲載内容の唯一の正本
src/layouts/DocumentShell.astro      共通HTML・SEO・文書構造
src/layouts/PlainLayout.astro        安全地帯となるPlain表示
src/styles/plain.css                 Plain専用CSS
src/layouts/*Layout.astro            お着替えテーマのレイアウト
src/styles/themes/                   お着替えテーマのCSS
src/config/themes.ts                 テーマID・既定テーマの選択
src/pages/index.astro                正本と選択テーマを結合する入口
src/pages/plain.astro                常設のPlain確認ページ
public/                              公開アセット
index.html                           Astro障害時の最小静的フォールバック
```

### Content

`src/content/pages/gaiden.md` が掲載内容の唯一の正本です。

本文、沿革、役職、リンク、説明文などを、テーマ側へ複製してはいけません。

### Theme

テーマは掲載内容を受け取り、視覚表現だけを担当します。

テーマは交換可能であり、定期的に新しいものを追加します。

### Plain

Plainは白地・黒文字を基本とする、簡素で安定した表示です。

Plainは「地味だから後で豪華にする場所」ではありません。**意図的に退屈で、依存が少なく、壊れにくいこと**が役割です。

### Static fallback

リポジトリ直下の `index.html` はAstroの通常Productionでは配信しません。

Astro、依存関係、ビルド系などが使用できない非常時に、Cloudflare Pagesを一時的な静的公開へ戻すための最終退避用です。詳細本文を二重管理せず、最低限のサイト識別情報だけを持たせます。

## 3. テーマ作業で守るもの

新しいテーマを作る作業では、次を**保護対象**とします。

### 原則として変更しない

- `src/content/pages/gaiden.md`
- `src/layouts/PlainLayout.astro`
- `src/styles/plain.css`
- `src/pages/plain.astro`
- リポジトリ直下の `index.html`
- 過去テーマのレイアウトとCSS
- canonical URLや主要リンクなど、掲載情報の意味

デザイン上の都合だけを理由に、これらを変更してはいけません。

### 共通基盤は慎重に変更する

`src/layouts/DocumentShell.astro` や `src/pages/index.astro` は複数テーマが共有します。

新テーマのために変更する場合は、既存テーマとPlainを壊さない後方互換な変更にしてください。テーマ固有の表現は可能な限りテーマ側へ閉じ込めます。

### 内容を「改善」しない

AIやデザイナーは、テーマ実装の一環として文章を要約、再編集、言い換え、削除、追加しません。

文章変更が必要に見える場合は、デザイン作業とは別の編集タスクとして扱います。

## 4. 新しいお着替えテーマの作り方

### 4.1 新しいテーマは「追加」する

新テーマは、既存テーマを書き換えるのではなく、新しいレイアウトとスタイルとして追加します。

例：

```text
src/layouts/Kinetic2026Layout.astro
src/styles/themes/kinetic-2026.css
```

必要な画像やフォント等のテーマ固有アセットを置く場合は、衝突を避けるため次のようにテーマ単位でまとめることを推奨します。

```text
public/themes/kinetic-2026/
```

### 4.2 テーマIDは一度公開したら意味を変えない

テーマIDは `src/config/themes.ts` の `THEME_IDS` に登録します。

テーマ名には年や時期などを含め、後から見て識別できる名前を推奨します。

例：

```text
editorial-2026
kinetic-2026-autumn
neo-print-2027-spring
```

同じIDのまま全面的に別デザインへ置き換えないでください。大きく着替える場合は新しいIDを作ります。

### 4.3 過去テーマを消さない

新テーマの追加と同時に、以前のお着替えテーマを削除してはいけません。

過去テーマは、デザインの履歴、比較対象、ロールバック候補として保持します。

古いテーマに問題があっても、まず「非既定」にして残すことを優先します。セキュリティや重大な依存問題など、保持自体が危険な場合だけ別途削除を判断します。

## 5. 実験してよいこと

お着替えテーマは、**先進的・実験的であることを歓迎**します。

たとえば、次のような表現や技術を検討できます。

- 大胆なタイポグラフィとグリッド
- container queries
- View Transitions
- scroll-driven animations
- variable fonts
- CSSの新しいレイアウト・色・タイポグラフィ機能
- SVG、Canvas、WebGL等を使った補助的な表現
- インタラクティブな視覚効果
- その時点で新しいブラウザ表現手法

これは例であり、採用を義務づけるものではありません。

### 実験テーマの最低条件

先進的なテーマでも、次は守ります。

- 本文は最終HTMLに存在し、JavaScriptが失敗しても主要情報を読める
- 外部フォント、画像、API等が取得できなくても本文が消えない
- モバイルでも全内容に到達できる
- キーボード操作とフォーカス表示を失わない
- `prefers-reduced-motion` を尊重する
- 文字拡大で主要情報が欠落しない
- 見た目のために見出し階層やリンクの意味を壊さない
- 装飾が壊れても、情報自体は残るようにする

つまり、**progressive enhancementを基本姿勢とし、実験的な表現を情報公開の前提条件にしない**ことです。

## 6. Plainのルール

Plainは、他テーマとは目的が違います。

### Plainでやらないこと

- 実験的なUI
- 複雑なアニメーション
- JavaScript必須の表示
- 外部サービスへの依存
- テーマ固有の大胆な装飾
- お着替えテーマと同期した再デザイン

### Plainで優先すること

- 白背景
- 黒を基本とする本文
- 普通に読めるゴシック系フォントスタック
- 単純な文書フロー
- 十分なコントラスト
- 少ない依存
- 予測可能なHTML
- 速く確実に情報へ到達できること

Plainは、通常テーマがどれだけ大胆になっても影響を受けないように保ちます。

`/plain/` は常設確認URLです。新テーマ開発中も定期的に開き、壊れていないことを確認します。

## 7. Figma・AIへ渡すときの指示

Figma、デザインAI、実装AIへテーマ作業を依頼するときは、少なくとも次を読ませます。

1. `docs/THEME_IMPLEMENTATION_RULES.md` — この文書
2. `src/content/pages/gaiden.md` — 実際に表示する全内容
3. `src/config/themes.ts` — テーマ登録方法
4. `src/layouts/DocumentShell.astro` — 共通文書構造
5. `src/layouts/PlainLayout.astro` — 退避先の存在を理解するため
6. 既存のお着替えテーマ — 過去テーマを上書きしないため

### Figma・デザインAIへの基本ブリーフ

次の考え方で依頼します。

- 外電通信は、定期的に外観を大胆に着替える公式サイトである
- 新テーマは、その時点の先進的なWebデザインや実験的な表現を試してよい
- 既存テーマの延長線にする必要はない
- 掲載文章は変更せず、与えられた全内容をデザインする
- デスクトップとモバイルの両方を設計する
- hover、focus、active等の状態も示す
- 本文量の増減に耐える
- アクセシビリティと可読性を、見た目の実験と両立させる
- Plainと静的fallbackは別系統なので、新テーマに合わせて再設計しない

### 実装AIへの最重要指示

> `gaiden.md`、Plain、`index.html`、既存テーマを壊さず、新しいテーマIDとして追加すること。

## 8. 推奨実装フロー

1. この文書と `gaiden.md` を読む。
2. 現在のテーマ構造と `themes.ts` を読む。
3. 新しいデザインコンセプトを決める。
4. 新規レイアウト・CSS・必要なアセットを追加する。
5. 新しいテーマIDを `THEME_IDS` に登録する。
6. `PUBLIC_GAIDEN_THEME=<new-theme-id>` でローカルまたはPreview確認する。
7. `npm run build` を成功させる。
8. 新テーマで `gaiden.md` の全内容が表示されることを確認する。
9. `/plain/` が以前と同じように読めることを確認する。
10. 既存テーマが残っていることを確認する。
11. Previewで承認後にのみ、新テーマを既定へ切り替える。

**新テーマの作成と、既定テーマへの昇格は別の判断**として扱います。

テーマを実装しただけで自動的にProductionの既定へしないでください。

---

## 9. 公開前チェック

新テーマをProductionの既定へ昇格する前に、最低限次を確認します。

- [ ] `npm run build` が成功する
- [ ] トップで全本文を読める
- [ ] モバイルで横スクロールや欠落がない
- [ ] キーボードだけでリンクへ到達できる
- [ ] focus状態が見える
- [ ] 200%程度の文字拡大で主要情報が消えない
- [ ] reduced motion環境で利用できる
- [ ] JavaScriptを無効化・失敗させても主要本文を読める
- [ ] 外部アセットが失敗しても本文を読める
- [ ] canonical、description等の基本メタ情報が維持される
- [ ] `/plain/` が正常
- [ ] 過去テーマが削除されていない
- [ ] `index.html` が不用意に変更されていない

---

## 10. 退避・ロールバックの順序

問題が起きた場合、完成度より**情報公開の継続**を優先します。

### レベル1：新テーマだけが壊れた

まず `plain` へ戻します。

方法：

- Cloudflare Pagesで `PUBLIC_GAIDEN_THEME=plain` を指定して再デプロイする
- または `src/config/themes.ts` の `DEFAULT_THEME` を `plain` に戻す

新テーマの修正は、Plainで公開を維持した状態で行います。

### レベル2：共通Astroコードに問題がある

共通変更を戻し、Plainでビルドできる状態を最優先で復旧します。

新テーマのために共有基盤へ大きな変更を入れない設計にしておくことが、この退避を容易にします。

### レベル3：Astroやビルド経路自体が使えない

リポジトリ直下の `index.html` を使う静的公開へ一時退避します。

このファイルは「完全版サイト」ではなく、外電通信の存在と最低限の情報を公開し続けるための最後の手段です。

---

## 11. 既存テーマの扱い

過去のお着替えテーマは、原則としてリポジトリに残します。

テーマの履歴そのものを外電通信のデザイン資産として扱います。

新テーマ開発者は、以前のテーマを「不要コード」とみなして掃除しません。

整理が必要になった場合は、新テーマ実装とは別タスクとして判断します。

---

## 12. このルールを変えるとき

この文書は、テーマより長く生きるルールです。

新しいブラウザ技術や運用方法に合わせて更新して構いませんが、次の3つは原則として維持します。

1. **内容の正本を一つに保つ**
2. **Plainという安全地帯を常設する**
3. **新テーマ追加時に過去テーマと最後の退避経路を壊さない**
